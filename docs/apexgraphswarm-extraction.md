# ApexGraphSwarm extraction audit

## Scope and finding

This is a source audit of the current optional Next.js graph workspace and its adapters. It is not a claim that ApexGraphSwarm exists as a separate repository or that the current application can operate a 300-agent production swarm. The current workspace has bounded graph analysis, an opt-in model review/team, four pinned local solver adapters, several configured remote-framework adapters, and a loopback harness bridge. Its durable coordination, tenant isolation, secret brokering, workspace isolation, and multi-worker recovery layers are not implemented.

The graph workspace is independently useful, but it is currently embedded in `play-anything`: `apps/web/scripts/prepare-assets.mjs` calls the legacy Python site builder and copies its graph JSON; the legacy creator page embeds `/graph` in an iframe and forwards graph snapshots by `postMessage`. Extraction should preserve this integration as an optional compatibility adapter while removing the RPG application as a runtime dependency.

### “300 agents” versus execution capacity

The application currently has three local specialist roles, three model-team calls in sequence/fan-out shape, and an integration runtime configured for two active jobs per Node process. The local harness bridge also caps active child processes at two. These are unrelated bounded limits, not evidence of 300 simultaneous workers, model calls, GPUs, or API capacity. A future product may represent 300 logical agent/task records while scheduling only a separately configured small number of active executions. Capacity must be established with measured load, provider quotas, per-tenant fairness and failure tests; no 300-agent throughput or latency claim is supported by this source audit.

## Extraction boundary

### Extract or port behind stable, domain-neutral interfaces

- `apps/web/lib/graph.ts`: snapshot schema, validation, evidence and limits, graph indexing, directed path semantics, neighborhood and filtered/capped views. Keep graph IDs and evidence semantics stable; version the schema before changing it.
- `apps/web/lib/analysis.ts` and `analysis.worker.ts`: deterministic local specialist computations and evidence reconciliation. Move UI worker construction into a client adapter; keep pure algorithms importable in a service package.
- `apps/web/lib/orchestrator.ts`: client-local orchestration behavior is a useful contract reference (roles, bounded concurrency, timeout and cancellation), but do not copy its in-memory state as the new durable scheduler.
- `apps/web/lib/model-swarm.ts` and `model-review.ts`: preserve explicit invocation, schema-validated output, tool/citation checks, bounded graph tools and partial/disagreement semantics. Move provider credentials and execution to a server worker; keep browser UI free of provider secrets.
- `apps/web/lib/integration-runtime.ts`, `framework-adapters.ts`, `hermes-adapter.ts`, `integration-catalog.ts`: port each adapter behind a typed, versioned capability interface, including source/endpoint provenance and explicit supported operations. Preserve provider-specific distinctions, cancellation limitations and acknowledgment-vs-completion behavior.
- `apps/web/integrations/kernel_runner.py`: port as a separately sandboxed solver adapter or package. Preserve the exact pinned revisions and request caps; keep Python standard-library-only operation where possible. Validate untrusted inputs before invoking upstream solvers and retain warnings for upstream claims that the adapter cannot verify.
- `integrations/harness_runner.py`: retain only as an optional local execution bridge. Its fixed-profile security boundary is a useful adapter, but it is not the durable job system and its configured CLI subscription profile is not a provider API entitlement.
- `apps/web/lib/neo4j-store.ts`: optionally port as a graph-repository implementation after adding tenant-scoped authorization and lifecycle policy. Do not reuse the current configured namespace as a substitute for tenant access control.

### Leave behind or remove from the ApexGraphSwarm core

- Do not import `play_anything.engine.PlayAnythingEngine`, `WorldState`, `QuestPath`, `DungeonRoom`, `SkillNode`, player wallet/reward/tokenomics, boss battle, NPC/voice, leaderboard, onboarding/age matching, Realm publishing/monetization or “whale” economy types into the new core. These are gameplay/product concerns, not graph execution contracts. The old engine facade and its RPG-specific data models live in `play_anything/engine.py`, `play_anything/adapters/repo_rpg_generator.py`, `play_anything/core/models.py`, `quest_steiner_synthesizer.py`, `dungeon_partitioner.py`, `skill_tree_induction.py`, `personalization_engine.py`, `tokenomics_equilibrium.py`, `realm_studio.py`, `strategic_whales_consortium.py`, and `dashboard.html`.
- Do not copy the legacy dashboard wholesale. `apps/web/scripts/prepare-assets.mjs` currently builds/copies the legacy creator site and installs an iframe bridge; make that bridge an optional, separately versioned compatibility frontend or retire it after the standalone app has equivalent graph import/export.
- Do not treat simulated cloud/KVM replicas or model-router price calculations in `play_anything/core/enterprise_infra.py` as deployed infrastructure, actual vLLM capacity, a sandbox, or a secrets system. The AGENTS contract specifically identifies these as simulations absent real hardware/cloud integration.
- Do not fold the current UI, server route, and persistence details into the graph domain package. Extract schema/algorithms separately from Next.js transport, durable control-plane, provider workers, and UI.

## Proposed professional architecture

1. **Extraction and provenance baseline.** Create a clean new project from a curated file manifest, not by moving the current working tree. Preserve the existing source repository and dirty work. Capture the original branch/HEAD, `git status --short`, staged/unstaged binary-safe diffs, and untracked-file inventory in a private handoff record. Keep `.env*`, `apps/web/.env.local`, tokens, generated credentials, `node_modules`, `.integration-sources`, runtime data and local profiles out of the new repository. Copy only reviewed files and tests; preserve their license/NOTICE files and each source project’s attribution. Pin upstream solver source revisions and verify them against a committed provenance manifest and content hashes. Do not silently rebase/replace a source pin.
2. **Domain package and versioned contracts.** Define versioned `GraphSnapshot`, `AnalysisRequest`, `Finding`, `AgentTask`, `ExecutionAttempt`, `Job`, and `JobEvent` contracts with schema validation at every trust boundary. Keep parsed/observed/inferred evidence distinctions and snapshot identity. Separate deterministic graph analysis from framework/provider adapters. Make every result carry input snapshot identity, source revision/model/provider where applicable, limits applied, and partial/uncertain status.
3. **Control plane with durable state.** Replace the process-local `Map` and queue with a transactional database plus queue/outbox. Submission accepts a tenant-scoped idempotency key and returns a durable job ID. Persist immutable job input/reference, status transition, attempts, timestamps, cancellation request, result digest, usage and error code. Use monotonic event sequence numbers and replayable SSE or WebSocket delivery; notifications are hints, database events are authoritative. Document delivery as at-least-once and require idempotent side effects rather than promising exactly-once execution.
4. **Leases and recovery.** Workers atomically claim jobs with tenant/resource-aware leases, heartbeat before expiry, and record attempt/lease generation. A reaper requeues expired safe-to-retry jobs and marks ambiguous external side effects for reconciliation instead of blindly replaying them. On process restart, jobs remain queryable, active leases expire, queued work drains, and cancellation is reconciled. Every adapter declares whether it supports cancel, status polling, idempotent start, and remote reconciliation.
5. **Identity, secrets and isolation.** Authenticate users/organizations before catalog/graph/job access; enforce tenant scope in both queries and storage keys. Use a server-side secret broker/vault with scoped short-lived credentials and redacted logs; never persist plaintext keys in job inputs/events. Run repository analysis in managed worktrees or read-only snapshots, with explicit filesystem/network/tool allowlists, cleanup policy, resource quotas and audit trail. Keep trusted local CLI execution separate from provider API-key execution.
6. **Bounded logical-agent scheduler.** Represent desired “300 agents” as 300 logical identities/tasks or graph-plan entries. Apply explicit limits independently for active model calls, local CPU jobs, subprocesses and remote API requests. Start from conservative configurable pools (the existing two-active integration jobs is a baseline, not a capacity promise); use fair tenant queues, token/cost ceilings, deadlines, cancellation and backpressure. Increase concurrency only after capacity/load tests and provider quota review.
7. **Operations and product boundary.** Provide job/event inspection, per-tenant usage, operator pause/drain, dead-letter review, source pin upgrades, policy/config validation and backup/restore. Keep “implemented”, “configured”, “unsupported” and “proposed” separate in UI/API. Expose a capability only when its adapter configuration and required lifecycle semantics are present.

## Acceptance gates before calling the extraction production-ready

- **Clean extraction:** build and tests pass from a clean checkout with no import/runtime dependency on `play_anything`; optional legacy bridge can be disabled and standalone graph import/export still works. No credentials, private profiles, generated `.env` files or local source clones appear in the new repository or its build artifacts.
- **Compatibility and provenance:** golden fixtures prove snapshot parsing, identity, evidence labels, directed path behavior and constraint warnings survive extraction. CI verifies all four source SHAs, license notices and checksums; changing a pin requires an explicit reviewed update.
- **Durability:** enqueue jobs, kill/restart the API and workers, then verify queued work resumes, completed results remain readable, an expired lease is reclaimed, event sequence has no gaps, and duplicate idempotency-key submissions return the same logical job. Test ambiguous external submissions without unsafe duplicate execution.
- **Cancellation and deadlines:** cancellation is persisted and observed by local workers; remote adapters report unsupported/best-effort semantics honestly. Enforce a server-side total deadline, per-provider deadline and cleanup of orphaned child processes/worktrees after timeout or worker death.
- **Security and tenancy:** automated cross-tenant negative tests for graph, job, event, result, usage and cancellation reads/writes; secret canary strings absent from API errors, logs, job rows and events; reject request-selected URLs, shell commands, paths, model IDs or unallowlisted tool operations.
- **Resource bounds:** test oversized graph, output, queue, prompt and event payload rejection; prove no silent truncation of solver inputs. Enforce per-tenant queue and active-work limits and backpressure under saturation.
- **300 logical records versus active work:** seed 300 logical tasks, verify all are queryable and auditable while active workers never exceed the configured pool. Measure throughput, p50/p95 queue delay and execution latency, memory, cancellation latency, failure/retry rate and provider cost at staged active limits. Publish the tested active concurrency, hardware, model/provider quotas and workload mix; do not infer it from a logical count.
- **Operational recovery:** exercise drain/pause, dead-letter inspection, adapter health/config checks, backup/restore and source-pin rollback. SLOs should be set from these measurements rather than guessed in this audit.
